# Decision engine and export contract

Contract version: `brief-decisions-v1`. Outputs describe investigation hypotheses
for analyst review. Role strength and priority are heuristic indices, not calibrated
probabilities, validated labels, complete account balances, or findings of guilt.

## Export contract for Member 3

`write_exports(features, clusters, out_dir)` keeps its existing arguments. It writes
these **exact ordered schemas**, with no additional CSV columns:

```text
nodes_roles.csv: gid,role,role_score,cluster_id,priority_score,evidence
clusters.csv: cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis
top_nodes.csv: rank,gid,role,priority_score,why
```

The strict node CSV is authoritative for its six fields. Gids are signed int64
integers, never floating point. Read browser identifiers as decimal strings.
Cluster identifiers, populations and ranks are integers; scores and amounts are
finite numeric values. Scores are bounded by [0,1]. Evidence is nonempty, contains
numeric support and is at most 200 characters. The top list is sorted by descending
priority, then ascending numeric gid; the exporter chooses 50 rows when available.
The technical brief requires at least 20 rows and sets no maximum.

`node_features.parquet` contains **one row per exact int64 gid**, with an ordinary
`gid` column and no serialized DataFrame index. It preserves every analytic column
passed to the exporter: graph/temporal/percentile/anomaly features, observation
flags, role diagnostics, priority contributions, and `priority_explanation`.
It also includes the six submission fields for convenient inspection; they must
match the strict CSV and must never override it in a consumer join. DataFrame
`attrs` are not part of the contract.

Member 3 should load both artifacts, validate unique/equal gid sets, drop the five
overlapping non-key fields from the auxiliary frame, then join it to the strict
node table one-to-one on gid. Do not join through float identifiers. Feature
columns may contain missing values when observations are unavailable; display
them as unavailable, not as observed zero. New optional feature columns are
additive and do not automatically become scoring inputs.

Decision APIs retain their current signatures. `assign_roles(features)` returns
gid, role, role_score **plus rule diagnostics**; merge the whole result one-to-one.
`score_priority(features, roles)` returns the enriched frame, including contribution
columns and the independent readable `priority_explanation`. `add_evidence(frame)`
adds the short role explanation. `cluster_graph(graph, nodes)` still returns
assignments and community metadata. `resilience_analysis(graph, features)` keeps
the baseline and top-1/5/10/20 removals.

The validator retains existing callers and adds optional raw-edge reconciliation.
Its CLI accepts `--data` for source nodes/edges. Use raw input reconciliation for
final acceptance. Member 3 owns pipeline orchestration, run metadata, dependency
pinning and the UI loader; those integration files are outside this change.

The full validator API is
`validate_submission(out_dir, expected_nodes=2248, source_nodes=None, features=None,
*, source_edges=None, graph=None)`. Supply either `source_edges` or `graph` for
independent directed-turnover reconciliation. The integrated pipeline supplies
raw edges and reconciles them with exported `internal_out_kzt`. The standalone
command performs the same independent source check:

```bash
python -O validate_submission.py --out ./out/brief-decisions --data ./data
```

Validation raises `SubmissionValidationError`, a `ValueError` subclass, and
remains active with Python optimization. `write_exports` returns its existing
`nodes_roles`, `clusters`, `top_nodes` counts plus `node_features`. No run metadata
is generated by this module; that remains Member 3's pipeline responsibility.

## Shared percentiles and missing observations

`P(x)` calls Member 1's `src.graph_features.percentile_rank`: average tied ranks
divided by the number of nonmissing observations. A single valid observation
receives 1; an empty/all-missing group remains missing. A constant group of size
N receives `(N+1)/(2N)`, not zero and not necessarily a high signal. The decision
wrapper treats infinities and nonnumeric values as unavailable before ranking.
Ranks are recalculated across the supplied feature table, without gid-specific
rules. Member 1's current helper is the shared policy; no feature code is changed.

Missing structural measurements remain missing. For each role, score is
`sum(weight * available component) / sum(available weights)`. Zero is an observed
value and retains its weight; a missing component contributes neither numerator
nor denominator. No available weight gives score 0. Missing metrics cannot pass
their numeric eligibility gate. All component values and final strengths are
bounded by [0,1].

Inbound-dependent ratios are unavailable for seeds, depth >=4, or a true
`boundary_censored`/`truncated_by_depth` flag. Explicit `<metric>_valid` and
`<metric>_available` flags, when supplied, also gate use: false or missing flags
mean unavailable. The actual feature-producer flags are also honored:
`relay_2d_valid` for `relay_2d_ratio`, `same_day_flow_valid` for
`same_day_flow_ratio`, and shared `flow_share_valid` for `fanin_share` and
`fanout_share`. Every present flag must be true; a false/missing producer flag
cannot be overridden by a true legacy alias, or vice versa. Role scoring,
priority scoring and explanations share this flag policy.
The ratio fields are pass-through, retained share, flow balance,
outgoing relationship share and the two temporal ratios. The absence of a flag
column does not itself suppress a measurement. Negative/nonfinite ratios are invalid.
Positive observed incoming amount is required for pass-through, retained share
and balance. A missing retained share may be derived from valid pass-through as
`clip(1-pass_through, 0, 1)`; balance may be derived as
`clip(1-abs(1-pass_through), 0, 1)`. These describe the sample, not account balances.
An explicit false/missing validity flag also blocks these fallback derivations.

Temporal overlap is date-level evidence. It cannot establish intraday order or
that the same money moved onward. Relay is the share of **eligible incoming-active
dates** with any outgoing activity on D, D+1 or D+2. A date is eligible only when
D+2 is no later than the latest observed transaction date; incomplete follow-up
dates are excluded from both numerator and denominator, even if an early outgoing
observation exists. `relay_2d_eligible_days`, `relay_2d_matched_days` and
`relay_2d_censored_days` expose this calculation. No eligible date makes relay
unavailable, rather than zero. Same-day ratio is the share of outgoing amount on
incoming-active dates. Both ratios are unavailable for seeds and depth-4 nodes;
decisions honor the producer flags and do not infer completeness from a zero.

## Role formulas, gates and rationale

Every structural candidate must pass its gate **and score >=0.55**. These are
transparent heuristic thresholds chosen to require several supporting signals;
they are not learned boundaries or estimates of criminality. Degree counts
distinct directed counterparties; transaction counts and observed KZT amounts
remain separate signals. Seed reach means directed reachability from supplied
seeds within the feature layer's four-hop scope, including a seed's own zero-hop
reach. `clip(x)` below means `min(1, max(0,x))`.

| Role | Weighted score before missing-weight renormalization | Structural gate |
|---|---|---|
| Consolidator | `0.30 P(in_deg) + 0.20 P(in_tx) + 0.20 P(in_kzt) + 0.20 P(seed_reach_count) + 0.10 retention` | At least 2 incoming counterparties, and either seed reach >=2 or incoming-degree percentile >=0.80. |
| Distributor | `0.40 P(out_deg) + 0.20 P(out_tx) + 0.20 P(out_kzt) + 0.10 fanout_share + 0.10 P(cross_cluster_out_deg)` | At least 2 outgoing counterparties. |
| Transit | `0.25 balance_score + 0.20 relay_2d_ratio + 0.20 P(betweenness) + 0.15 P(in_deg) + 0.15 P(out_deg) + 0.05 same_day_flow_ratio` | Positive incoming and outgoing degrees, and valid observed pass-through in [0.5,1.5] inclusive or valid two-day relay >=0.50. |
| Coordinator | `0.25 P(seed_reach_count) + 0.25 P(betweenness) + 0.15 P(pagerank) + 0.15 P(cross_cluster_degree) + 0.10 P(in_deg) + 0.10 P(out_deg)` | At least 2 of seed reach, betweenness, PageRank and cross-cluster degree at percentile >=0.90, plus at least 1 observed relationship. |
| Terminal | `0.50 no_outgoing_signal + 0.20 retention + 0.15 P(in_kzt) + 0.10 P(in_tx) + 0.05 P(in_deg)` | Nonseed, depth <4, uncensored boundary flags, positive incoming degree and amount, nonnegative outgoing amount <=10% of incoming, and either outgoing degree zero or valid pass-through <=0.10. |
| Peripheral | Fallback defined below; no independent weighted formula. | No structural candidate reaches eligibility and strength >=0.55. |

`no_outgoing_signal` is 1 when observed outgoing degree and amount are both zero
and incoming amount is positive; otherwise it is `clip(1-pass_through/0.10)` where
the ratio is valid. It is unavailable for seeds and depth >=4. `fanout_share`
comes from the feature layer's outgoing share of incident relationships. The
role engine does not estimate missing seed or boundary ratios.

Consolidation emphasizes fan-in and convergence; distribution emphasizes fan-out.
Transit needs actual incoming/outgoing relationships and observed flow or timing
support. Coordination requires multiple strong signals, while its activity gate
prevents singleton percentile ranks from making an isolate a coordinator.
Terminal describes little observed outgoing flow inside the observation window;
the depth and seed exclusions prevent censoring from becoming endpoint evidence.

Among eligible structural roles, the largest score wins. Exact score ties use:
**coordinator, consolidator, distributor, transit, terminal, peripheral**.
Peripheral strength is the highest score among candidates passing a structural
gate but falling below 0.55; it is **0 if no structural gate passes**. Thus a
no-activity isolate is not assigned spurious positive membership evidence.
`role_best_candidate` and `role_best_candidate_score` expose that selection.

Compared with the audited implementation, this version fixes singleton ranks,
keeps missing percentiles explicit, suppresses unavailable boundary ratios, uses
the actual balance formula when deriving it, adds the coordinator activity guard,
requires positive observed inflow for terminal, and removes the artificial
0.549999 fallback for gate-failing nodes. These changes follow observation and
rule semantics; they are not tuned to any gid, role count or cluster count.

## Priority and its explanations

Review priority is the following sum, clamped to [0,1]:

| Term | Weight | Value |
|---|---:|---|
| role_strength | 0.25 | Selected role_score |
| seed_reach_count | 0.20 | P(seed_reach_count) |
| betweenness | 0.15 | P(betweenness) |
| pagerank | 0.10 | P(pagerank) |
| total_kzt | 0.10 | P(observed incoming + outgoing KZT) |
| cross_cluster_degree | 0.10 | P(cross_cluster_in_deg + cross_cluster_out_deg) |
| temporal_signal | 0.05 | Maximum available valid relay/same-day ratio |
| peer_anomaly_score | 0.05 | Member 1's bounded depth-peer anomaly score |

Priority uses fixed weights. Missing terms contribute **0 without weight
renormalization**; availability flags distinguish missing from measured zero.
All eight `priority_<term>_contribution` fields sum to `priority_score`, while
`priority_<term>_value` and `priority_<term>_available` expose the inputs. Incoming
plus outgoing turnover is an activity measure and may count an internal transfer
at both endpoints; it is not a balance. A percentile of observed zero can be
positive because tied ranks are relative to this dataset.

`priority_explanation` names the three largest positive additive contributions,
their actual values/percentiles, and their added score points. Equal contributions
use table order above. `top_nodes.why` copies this ranking explanation, independently
of `evidence`, which explains the assigned role. If no contribution is positive,
the reason explicitly says so. Optional new routes, motifs or anomalies remain
available in Parquet and have no scoring effect unless formulas and tests change.

## Clusters and resilience

Only Louvain receives an undirected projection. Nodes and directed edge pairs
are inserted in ascending exact numeric gid order; parallel amounts and reciprocal
A-to-B/B-to-A amounts are summed using canonically ordered `math.fsum`. All supplied
isolates enter before clustering. The directed input remains unchanged.
Louvain uses `weight="sum_kzt", resolution=1.0, seed=42`. Empty/zero-turnover
graphs have singleton communities because modularity has a zero denominator.
There is no target cluster count. Reproducibility is tested within the installed
versions; Member 3 must pin dependencies for reproducibility across installations.

Cluster IDs start at 0, sorted by descending seed count, descending directed
internal turnover, then minimum numeric gid. Cross-cluster in/out degrees count
directed relationships and their total is the sum; a reciprocal pair counts in
both directions. `cross_cluster_count` counts distinct adjacent other communities.
`internal_out_kzt` is each node's directed amount to its own community; summing it
reconciles internal cluster turnover without double-counting reciprocal transfers.

Cluster `top_gids` is a comma-separated list of up to five decimal int64 gids,
ordered by descending priority then ascending gid. Hypotheses use the first
matching condition in this order:

1. At least 2 seeds: multi-seed convergence community.
2. Mean incoming degree >1.25 times mean outgoing degree: collection-oriented structure.
3. Mean outgoing degree >1.25 times mean incoming degree: distribution-oriented structure.
4. At least 35% transit nodes: transit-heavy structure.
5. At most 3 nodes or at least 70% peripheral nodes: sparse peripheral community.
6. Otherwise: mixed-flow community.

These are structural summaries, not inferred unlawful purposes. Multi-seed
membership suggests a convergence hypothesis; it does not prove coordinated intent.

Resilience preserves the baseline and hypothetical removal of priority top
1/5/10/20, using the same priority/gid order. It reports `scenario`,
`removed_top_n`, `n_weak_components`, `largest_weak_component_size`,
`fraction_baseline_largest`, and `seeds_in_largest_component`. A tie between largest
weak components selects the one with minimum gid. Supplied isolates are retained.
Weak components describe connectivity, not Louvain communities. The ratios measure
structural concentration in the observed graph, not real-world disruption or
evidence of a criminal organization.

## Auxiliary fields and the one-minute explanation workflow

| Auxiliary fields | Type and purpose |
|---|---|
| gid | Unique, nonnull int64 key, identical to strict node CSV gids |
| Original graph/temporal/anomaly/observation fields | Preserved as supplied, with unavailable measures remaining null |
| role_rule, role_rule_details | Readable winning rule, actual component values, gates and effective denominator |
| role_best_candidate, role_best_candidate_score | Strongest structurally gated candidate, or `none` and 0 |
| role_<structural role>_score | Floating candidate score in [0,1] |
| role_<structural role>_gate / _eligible | Boolean structural gate / gate plus score >=0.55 |
| role_<structural role>_available_weight | Sum of usable formula weights, [0,1] |
| role_<structural role>_gate_reason | Readable threshold comparison using actual metrics |
| decision_<ratio>_valid | Boolean availability after decision observation protections |
| decision_<ratio> | Nullable numeric ratio actually used, after masking and derivation |
| decision_<metric>_percentile | Shared-policy percentile actually used by the role engine |
| priority_<term>_value / _available / _contribution | Normalized nullable input, boolean availability, nonnegative weighted contribution |
| priority_explanation | Independent readable ranking reason; source for top_nodes.why |
| cross_cluster_count / internal_out_kzt | Distinct adjacent communities / within-community observed outgoing amount |

For any supplied gid, read the strict role/evidence, then `role_rule_details` and
the candidate gate/score columns. Show the three leading priority contributions
using `priority_explanation`, and finally the seed/boundary/temporal availability
flags. These are direct lookups; no model/API call or recomputation is necessary.
The strict role may differ from the role a reviewer initially expects because the
engine chooses the largest eligible score, not the first structural label found.
